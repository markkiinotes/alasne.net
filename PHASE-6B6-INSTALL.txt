PHASE 6B.6 - STRIPE OPERATIONS & RECOVERY
=========================================

PURPOSE
-------
Turn Alasne's proven Stripe payment/refund lifecycle into an operable
Mission Control workflow.

Phase 6B.1 through 6B.5 established:
- signed/idempotent Stripe webhook ingestion
- webhook-authoritative payment finalization
- Stripe refund finalization and failure rollback
- refund notifications/reconciliation
- mixed-tender Stripe + store-credit checkout/refunds

Phase 6B.6 adds operational visibility and recovery when a webhook
fails locally, becomes stale, or never reaches Alasne.

FAILED / STALE WEBHOOK RETRY
----------------------------
POST /admin/stripe-operations/retry

The action:
1. requires CSRF
2. requires the event to exist in stripe_webhook_events
3. permits only:
   - status = failed
   - status = processing and stale for at least 5 minutes
4. retrieves the canonical Event directly from Stripe's authenticated API
5. reuses StripeWebhookService claim/retry logic
6. reuses the existing idempotent payment/refund finalizers
7. marks the webhook ledger processed or failed using normal logic

A processed event cannot be forcibly re-run through this control.

Because the Event is fetched over Stripe's authenticated API, this path
does not use or emulate Stripe-Signature. The public webhook endpoint
continues to require signature verification.

TRANSACTION RECONCILIATION
--------------------------
POST /admin/stripe-operations/reconcile

The action requires CSRF and scans up to the operator-selected limit
(default 100, maximum 500).

Eligible transactions are at least 5 minutes stale and have a Stripe
provider object ID.

Charges:
- local pending charges are eligible
- local failed charges whose order is still unresolved are also eligible
  so a later successful customer retry can be recovered if its success
  webhook was missed
- paid or canceled orders are excluded

Refunds:
- local pending refunds are eligible

For each eligible Stripe charge:
- retrieve PaymentIntent from Stripe
- succeeded -> StripePaymentFinalizer::succeeded()
- canceled -> StripePaymentFinalizer::canceled()
- requires_payment_method with a real last_payment_error and a local
  pending transaction -> StripePaymentFinalizer::failed()
- all other states remain waiting and are not forced

For each eligible Stripe refund:
- retrieve Refund from Stripe
- succeeded/failed/canceled -> StripeRefundFinalizer::finalize()
- nonterminal status remains waiting

Reconciliation never creates a new PaymentIntent, charge, or refund.
It only observes an existing Stripe object and applies the same
idempotent finalizers used by signed webhooks.
